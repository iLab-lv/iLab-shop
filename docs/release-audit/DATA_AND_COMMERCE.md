### DC-01 — Prove the production Firebase boundary before release (P1 release gate)

**Evidence.** Shop Admin and client initialization use environment variables (`lib/firebaseAdmin.js:8-23`, `lib/firebaseClient.js:6-20`). Repository architecture documents the intended shared project `ilab-v2` (`docs/architecture.md:15`). The checkout has neither `.firebaserc` nor `firebase.json`; `firebase.emulators.json:1-3` points at `firebase/firestore.proposed.rules`, whose first line labels it proposal-only and whose catch-all denies client access (`firebase/firestore.proposed.rules:1-13`). `firebase/storage.rules:1` describes itself as a test copy of the deployed Storage policy. The emulator runner forces `demo-ilab-shop-s21`, strips credentials, and pins all emulator hosts to loopback (`scripts/run-emulator-tests.mjs:7-16`); the harness independently refuses non-demo projects, external credentials, and non-loopback endpoints (`tests/emulator/support.mjs:27-61`).

**Impact.** The local evidence shows intentional safeguards and a safe emulator boundary, but it does not establish which Firebase project or rules are currently attached to the production Shop deployment. Shop and Service are intended to share `ilab-v2` while keeping Shop collections namespaced (`shopProducts`, `shopDevices`, `shopProductTypes`, `shopCarts`, `shopOrders`, `shopInvoices`, and `shopSettings`); the browser should have no direct access to these Shop documents. A mistaken live binding or permissive deployed rule would undermine that separation.

**Approach / effort / blocker.** Before release, verify the production deployment environment's public and server project IDs agree with the intended project, inspect effective deployed Firestore and Storage rules and indexes, and retain a concise deployment record. Use the existing project release process/read-only console or CLI inspection. This checkout alone cannot prove external deployment state; that external read access is the blocker to closing this gate. Do not deploy `firestore.proposed.rules` by inference: it intentionally permits reads from selected Service collections and denies all other client access, and is explicitly a proposal.

### DC-02 — Bound prices by supported Cart totals (P2)

**Evidence.** `lib/adminProductValidation.mjs:10-14` accepts any non-negative currency value whose converted cents are a safe integer. `lib/commerce.mjs:37-50` multiplies that price by quantity and adds line totals, checking only `Number.isInteger`, which is true for some unsafe integers. Quantity may be as high as 99 (`lib/commerce.mjs:6`, `26-34`). Order creation does reject an unsafe final total (`lib/shopOrders.js:74-78`).

**Impact.** A deliberately or accidentally extreme price can make Cart resolution return a rounded, unsafe total. The Checkout UI may display a value that does not exactly represent the intended integer cents, while the subsequent Order request is rejected as invalid. Ordinary product pricing is far below this range, so this is a defensive integrity issue rather than a likely customer-facing path.

**Approach / effort / blocker.** Choose an explicit maximum supported unit/line/order amount in the existing domain contract, or reject any multiplication/accumulation that is not a safe integer and present a useful Cart error. Keep this aligned across Admin validation, public Cart resolution, and Order creation. Small change; no external blocker. The maximum monetary value is a business constraint not currently specified by `docs/domain-rules.md`.

### DC-03 — Invoice PDF crash cleanup (P2 operational)

**Evidence.** Order and immutable Invoice snapshots are created transactionally, then PDF generation runs after commit (`lib/shopOrders.js:79-95`). Storage upload and Firestore finalization are separate operations (`lib/invoices/invoiceService.js:43-57`); errors are recorded as failed attempts while retaining the Order (`lib/invoices/invoiceService.js:70-87`). `docs/architecture.md` documents that a crash can leave a private orphan object.

**Impact.** A PDF render/upload failure does not roll back the order, which preserves purchase integrity. A hard process crash can leave an unreferenced object that the normal retry path cannot identify from invoice metadata. This is a storage hygiene and operations concern; generated objects are private and served through the authenticated invoice route.

**Approach / effort / blocker.** Define an operational retention/inspection process for unreferenced `shop/invoices/` objects, using a dry-run inventory before any cleanup. The existing application behavior is otherwise intentional; no order mutation is recommended here. Effort depends on whether a scheduled operational process is already available, which was not verified in this source-only audit.

## Data ownership and contracts

Shop’s written architecture and implementation consistently keep Service and Shop as separate applications on the intended shared Firebase project. Service owns the unprefixed repair/catalog data; Shop owns the `shop*` collections and shares `users/{uid}` as the authenticated profile. Shop Admin uses the Firebase Admin SDK (`lib/firebaseAdmin.js:8-32`) and validates writes server-side. Client-side Firestore access is not used for Shop products, settings, carts, orders, invoices, or inquiries; the browser uses Firebase Auth and Shop APIs. The emulator rule proposal denies all client access outside five public Service collections (`firebase/firestore.proposed.rules:5-13`).

Admin product serialization is intentionally privileged and contains cost, wholesale, retail, authoritative Model IDs, derived Series/Brand IDs, images, stock, and status (`lib/adminProducts.js:10-43`). Admin writes validate active Product Type, derive compatibility from actual Model → Series → Brand ancestry, and allocate immutable SKU values transactionally (`lib/adminProducts.js:71-89`; `lib/adminProductValidation.mjs:16-35`). Public Shop serializers whitelist fields and omit `purchasePriceCents`; wholesale is included only when the server resolves an authorized active profile (`lib/shopCatalog.js:7-11, 26-43`; `lib/shopProducts.js:8-12, 45-67`; `lib/commerce.mjs:20-24`; `lib/auth/roles.mjs:53-78`). Product compatibility is based on structured `modelIds`, with `seriesIds` and `brandIds` derived during Admin writes, matching the locked contract.

Contact, delivery fees, tax and pickup data flow through `shopSettings/general` and its pure normalization model, as described in `docs/architecture.md`; checkout re-reads current settings in its transaction. Product price and stock are re-read server-side at Order commit. No duplicate client pricing or direct-write path was found in the inspected flow.

## Dependency advisory triage (release evidence, not a confirmed exploit)

The read-only `npm.cmd audit --omit=dev --json` returned **12 affected package entries: 4 high, 8 moderate, 0 critical**. These include transitive/parent entries for the same advisory, not 12 distinct reachable attacks. Root `@grpc/grpc-js` is 1.9.16; the Admin `google-gax` chain has 1.14.5. Nested UUID 9.0.1 copies are also present; the root UUID is 11.1.1.

The maintainer's [gRPC advisory](https://github.com/grpc/grpc-node/security/advisories/GHSA-m9gg-hp2v-232j) concerns server certificate authentication using `getAuthContext` with optional client certificates; this app does not expose that server configuration in inspected source. The [UUID advisory](https://github.com/uuidjs/uuid/security/advisories/GHSA-w5hq-g745-h8pq) concerns v3/v5/v6 with caller-supplied output buffers. Application checkout/cart IDs use `crypto.randomUUID`, not those APIs. This is evidence against those specific direct app attack paths, not exhaustive dependency reachability proof. `lib/firebaseClient.js:4` still imports browser Firestore; review whether the exported client database is consumed before changing it.

Record a controlled dependency triage/update decision with Auth, Storage, Firestore, Invoice and emulator regression checks. npm's suggested Firebase 9.14.0 major change/downgrade is not an approved remedy, and no `audit fix`, package update or lockfile modification was performed. Advisory reachability and accepted residual risk remain a release gate excluded from confirmed P0/P1 defect totals.

## Product/import and operational completeness

`scripts/import-shop-catalog.mjs:14` explicitly expects 605 Products. It checks target collection emptiness before both modes (`:548-549`), defaults to dry-run (`:75,553`), requires `--write` for writes and uses create-only BulkWriter operations (`:450-451`). It therefore does not silently update existing Product records; it also is not a general incremental import into a populated catalog. No import or migration was run. The live sitemap contains 744 total URLs across route types; that is not evidence of 744 Products or of the exact historical import provenance. `scripts/migrate-shop-products-v2.mjs` was not executed. Any future transformation must explicitly scope imported records and preserve older records.

The runtime Product sample `back-camera-for-iphone-11` remains unpriced and displays one inquiry action. Its description repeats iPhone 11 compatibility several times, while the compatibility section correctly derives Model IDs. This demonstrates that the historical concise-description convention is not uniformly true in current content. Review imported and pre-existing records separately; do not mutate all descriptions or infer Model IDs from prose. This data-quality observation is included under AR-08's content-owner recommendation, not counted as another defect.

Checkout implements pickup, courier and Omniva parcel-machine details; delivery fees come from settings, and shipping snapshots are immutable. Cash-on-pickup and bank transfer are the only payment methods. No card gateway is present or required by the locked contract. Account order serialization deliberately supplies a display fallback for null pickup locations (`lib/shopOrders.js:108`), so the Account view's `pickupLocation.name` access does not establish a courier-order crash.

Order confirmation and Invoice download are implemented; real customer notification/email delivery is not demonstrated by an email-provider integration in the inspected order flow. Part inquiry email notification is explicitly documented as not implemented. This is an operational scope decision, not proof that a required payment gateway or email workflow is broken. Before opening sales, ensure staff actively monitor Orders/Inquiries and confirm the approved customer communication process. No real delivery/notification test was sent.
